# Q&A 预案

> 配套《我让一群 AI Agent 帮我做完了一个需求》分享会使用。
> 共 12 个高频问题，每个问题给出：**短答（30 秒版本）/ 展开（2 分钟版本）/ 避坑（不要说什么）**。
> 类别覆盖：能力边界、体验、成本/效率、风险/可靠性、产品设计启发、落地建议。

---

## 一、能力边界类

### Q1：AI 真的能独立写完一个需求吗？还是你中途偷偷改了很多？

**短答**：这个具体需求（前端 Demo 增量 + 部署）AI 独立完成了 ~85%，我实际动代码的行数是 0，主要工作是"给需求 + 确认选项 + 最后点链接验收"。但前提是仓库文档全、边界清、需求是增量小需求；换个场景这个比例会掉。

**展开**：
- 我没动过一行业务代码，但我做了几件比写代码更重要的事：把需求边界写清楚、选对仓库、在 Spec 阶段回复待确认问题、最后做用户视角验收。
- AI 独立完成的部分：读仓库规范、写新功能代码、修部署问题、写 E2E、跑 CR、部署验活——这些全是它闭环的。
- AI 没做的事：定义做什么/不做什么、判断产品合理性、架构级决策、最终上线拍板。
- 真实比例强烈依赖三个前提：**上下文是否充分、边界是否清晰、错了是否能回滚**。三个都满足，AI 能到 80–90%；缺一个就掉到 50% 以下。

**避坑**：
- 不要说"AI 完全独立做完，我什么都没干"——这会让工程师同事本能反感，也不符合事实。
- 不要说"AI 还是不行，还得人擦屁股"——这会忽略你真正在做的高价值工作（定义问题、判断品味、兜风险）。
- 不要给一个通用百分比，一定要说"这个需求是 X%，换类需求会不同"。

---

### Q2：测试是 AI 自动跑的？它怎么知道该测什么？

**短答**：测试用例是 AI 根据 Spec 的验收点自动生成的，执行是它自己跑、自己修、自己跑到绿的。但"测什么"这件事本质上还是由 Spec 决定的，它不会主动替你想"Spec 漏了什么"。

**展开**：
- 测试 Agent 读了仓库里的 `docs/agent-testing.md`，里面写了"用 getByRole、不用 waitForTimeout、首轮收集失败批量修复"这些规范，它真照做了。
- 它从 Spec 的验收标准反推 case，正反路径都覆盖，这一点比很多人工测试写得全。
- 但它有一个关键短板：**不会质疑 Spec**。Spec 漏写的边界它不会提。所以"测什么"的责任还是在写 Spec 的人和做产品判断的人身上。
- 我的建议是：把 AI 测试当"不知疲倦的执行者"，把人工测试当"质疑者+场景设计者"，两者结合。

**避坑**：
- 不要说"以后不需要测试同学了"——这会引发强烈反感，也不符合事实。
- 不要说"AI 写的测试比人好"——应该说"AI 写测试在覆盖度和执行耐心上比人好，在质疑和探索上比人差"。
- 不要回避"为过而过"的风险（AI 修到测试过但逻辑没真对），要主动承认这是需要 CR 兜底的。

---

### Q3：CR 是 AI 做的？它真能挑出实质性问题吗？

**短答**：CR 主要是 AI 做的，它在"一致性、约定、i18n 对齐、空值边界、代码风格"这几类问题上挑得比人细；但在"业务逻辑对不对、产品体验好不好"这类问题上，它挑不出来，必须人兜底。

**展开**：
- AI CR 擅长的：同语义不同类名、中英文文案没对齐、违反 AGENTS.md 的"不要做"、明显空值风险、死代码。
- AI CR 不擅长的：业务逻辑合理性、产品交互好不好、架构选择对不对、是否和产品目标一致。
- 信噪比上，它偶尔会提一些 nit 级别的风格建议，需要人筛一下；但不会放水，这点比人 CR 强。
- 我的看法：**AI CR 是非常好的"第一轮守门员"**，能帮人挡掉 80% 的低级错误，让人把精力集中在业务和产品判断上。

**避坑**：
- 不要说"AI CR 可以替代资深工程师 CR"——替代不了业务判断。
- 不要说"AI CR 没什么用"——它在一致性检查上的价值是真实的，能显著降低人工 CR 的认知负担。

## 二、体验类

### Q4：整个流程里，哪个瞬间你觉得最爽？

**短答**：两个瞬间：一个是它第一次吐出 Spec 的时候，300 字换回一份几千字、结构比我自己写得还规整的 PRD 雏形；另一个是我最后打开 Pages 链接，发现页面真的跑起来了、base 路径都修好了，那个"居然成了"的感觉。

**展开**：
- Spec 那个瞬间：我写得很随意，它回得很认真，而且主动列待确认问题——那种"被认真对待"的感觉是 Copilot 那种补全工具给不了的。
- 上线那个瞬间：我真的没动代码，十几分钟后打开链接页面能点、功能在、中英文都有、部署路径没 404。作为工程师大家都懂，"第一次打开就成了"是非常稀有的体验。
- 但要诚实讲，爽感有一部分来自"我本来没期望它这么成"——是**低预期 + 超预期交付**带来的，不是它真的做到了什么不可思议的事情。

**避坑**：
- 不要把爽感吹成"震撼""革命性"——这种词会让没亲身体验过的人觉得你在做广告。
- 不要顺带踩人工研发——"人做要一周 AI 做十分钟"这种话很得罪人，也不准确（人做一周里很大一部分是需求对齐、方案讨论、跨团队协作，不是写代码那十几分钟）。

---

### Q5：哪个瞬间让你最崩溃 / 最想上手接管？

**短答**：不是某个 bug，是它在写代码那段"沉默期"——我看不到它在干嘛、会不会卡住、方向对不对，那个等待的焦虑感比遇到具体 bug 还难受。

**展开**：
- 遇到具体 bug 反而不可怕，因为看到错误就能判断。真正难受的是"黑箱等待"，那种"它到底在不在干活"的不确定感。
- 第二个让我想接管的瞬间是纠错颗粒度不对——看到某行代码写得不对，但没有"在这一行上直接告诉它改"的入口，要退回到写一段评论让它重跑节点，这个认知负担让人烦。
- 第三个是"它成功了但我不信"——发布完我必须自己去点链接，这种"它说行我还得自己验"的感觉，是体验上的隐形税。
- 崩溃点几乎都不是"AI 做不到"，而是"**产品体验没给我足够的透明度和控制感**"。

**避坑**：
- 不要编一个"AI 写了一堆 bug 我收拾了半天"的爽文式崩溃——我这次确实没遇到这种戏剧性场面，要诚实。
- 不要把问题归到"模型不够强"，这些卡点主要是产品设计问题，不是模型能力问题。

## 三、成本/效率类

### Q6：整体比人做快多少？Token 成本大概多少？

**短答**：纯"从需求到上线"的墙钟时间大概是人的 1/5 到 1/3，但前提是需求小、上下文全。Token 成本我没拿到精确账单，按同类平台的经验大概是几元到十几元人民币级别，比人天成本低两个数量级。但这不意味着"AI 成本是人的 1/100"——因为人在定义问题、做判断、验收上的时间省不下来。

**展开**：
- 可量化的快：写代码、跑测试、等部署这些执行环节，AI 快很多。
- 不可量化的省不下来：需求澄清、边界定义、产品判断、业务验收、风险兜底。
- 真正的账要这么算：**AI 把"执行成本"打下来了，但"决策成本"还在，而且决策成本才是大头**。所以 AI 带来的不是"同样的事便宜 100 倍"，而是"单位时间里团队可以尝试更多的可能性"。
- 成本上要警惕隐性成本：等待的焦虑、纠错的认知负担、万一翻车要回滚的成本。这些不算 token 账单，但算人的心理账户。

**避坑**：
- 不要说"AI 能让研发效率提升 10 倍"——这种 PR 数字很容易被工程师一句话戳穿。
- 不要拿"写代码速度"直接对比"人天"，人天里很大一部分不是敲键盘。
- 不要给没核实过的具体成本数字（比如"一次几毛钱"），不清楚就说"没拿到精确账单"。

---

### Q7：是不是以后小需求都不用排期了，直接丢给 AI？

**短答**：**小 + 边界清 + 错了能回滚**的需求可以试点，但"不用排期"是个误解——需求本身还是要想清楚，只是执行可以更轻量。

**展开**：
- 可以直接丢给 AI 的典型需求：文档生成、单页小功能、测试用例补全、CR 辅助、重复性代码改造、一次性 Demo。
- 不能直接丢给 AI 的：涉及核心链路、数据变更、权限安全、对外承诺、需要多团队对齐的需求。
- 即使是"直接丢给 AI"的需求，也还是需要人做三件事：写清楚边界、过 AI 产出的 Spec、做最终验收。
- 更准确的说法是：**排期不会消失，但排期的重量会变化**——原来要排 3 人天的小活，可能变成"丢给 AI 半天 + 人 1 小时验收"，这部分产能会被释放出来做更重要的事。

**避坑**：
- 不要画"以后 PM 直接写需求 AI 直接上线"的大饼——中间的产品判断、风险把关是省不掉的。
- 不要给团队一种"大家都要失业了"的焦虑感，这会让分享变味。

---

## 四、风险/可靠性类

### Q8：AI 写的代码敢直接上线吗？出错了谁背锅？

**短答**：内部工具、Demo、非核心链路、可快速回滚的，我敢上；涉及用户资金、数据、权限、对外 SLA 的，今天还不敢直接上。出错的锅必须人来背——AI 是工具，Owner 永远是人。

**展开**：
- 我这次敢直接部署，因为是 Demo 站点、没有后端、没有用户数据、错了回滚成本为 0。
- 判断能不能上线的维度不是"是不是 AI 写的"，而是"错了的爆炸半径有多大、回滚有多快、监控和验收能不能兜住"。这三个答案都令人放心，谁写的都能上；任何一个不放心，人写的也不能贸然上。
- 关于背锅：**AI 不背锅**。未来组织里要明确——需求 Owner、代码合并人、上线审批人，这三个角色必须是人，且责任清晰。AI 可以做执行，但责任主体不能转移。
- 好消息是，AI 在"一致性检查""测试覆盖""遵守规范"上的能力，实际上能降低一部分低级错误上线的概率。

**避坑**：
- 不要说"AI 写的代码比人写的 bug 少"——样本不足，且 bug 的类型和人写的不一样。
- 不要说"出了问题找 AI 提供商"——企业内部使用责任是自己的。
- 不要用"AI 也会出错所以别用"式的保守结论，也不要用"人也会出错所以一样"式的和稀泥。

---

### Q9：它会不会"胡说八道"或悄悄改你没让它改的东西？

**短答**：会有"做超出 Spec 的事"的倾向，但我这次没遇到它乱改核心代码或编造不存在的 API 的情况。关键在于**把"不要做什么"写清楚**，并且有 CR 和测试兜底。

**展开**：
- AI（特别是 LLM）天然有"补全"倾向——你让它做 A，它可能顺手把它觉得相关的 B 也做了。这次它主动改了 vite base 是正面例子（因为不改主任务不成立），但其他场景下可能是越帮越忙。
- 控制它不乱动的手段：AGENTS.md 里写清楚"不要做"清单；CR Agent 对 diff 做审查；保持每步产物可 diff、可回滚。
- 关于"幻觉"：在代码场景下它的幻觉比纯文本场景少，因为代码有编译器/测试/运行三重验证，错了很容易被抓；但它会"误解需求"，这比纯幻觉更常见。

**避坑**：
- 不要说"AI 很规矩从不乱动"——它是有外扩倾向的，必须约束。
- 不要说"AI 天天乱改代码根本管不住"——只要规则、CR、测试三件套到位，是可控的。

## 五、产品设计启发类

### Q10：如果我们自己做 AI 产品，最该"抄"哪一点？最该避开哪个坑？

**短答**：最该抄的是"**让 Agent 先读规则再动手**"——AGENTS.md + 自动加载 + 版本化这个模式，是 AI 协同的地基。最该避开的坑是"**把全自动当作目标**"——为了全自动把 HITL、可解释性、接管通道都省了，短期看酷炫，长期用户不敢用。

**展开**：
- 为什么 AGENTS.md 模式值得抄：它把"上下文"从用户每次的 prompt 里抽离出来，变成可沉淀、可迭代的资产。所有做得顺的 AI 产品都有类似机制（系统 prompt、项目设定、技能包、知识库），只是名字不同。
- 为什么"全自动崇拜"是坑：AI 今天还会错、还有边界、还会幻觉，如果产品设计让用户在关键节点无法介入、看不懂、接不住，用户试用一次就不敢再来。**AI 产品的信任是建立在"随时能接管"之上的，不是建立在"不用你管"之上的。**
- 我自己的排序：**可解释 > 可追溯 > 可接管 > 智能感**。前三个做好了，智能感差一点用户也愿意用；前三个没有，再聪明用户也不敢放正事上来。

**避坑**：
- 不要把"抄"理解成"做个 AGENTS.md 文件名就完了"——重点是规则被自动加载、被强制执行、能被迭代。
- 不要在分享里直接 diss 友商产品"做得差"，只说通用设计原则。

---

### Q11：你觉得 AI 产品体验的下一个竞争点是什么？

**短答**：我觉得是**"让用户在'放权'和'接管'之间顺滑切换"**——也就是 HITL 的颗粒度和反馈通道。前两年大家在拼"模型有多聪明"，接下来拼的是"用起来有多安心"。

**展开**：
- 模型能力大家都在趋同，差异化越来越小。真正拉开差距的是产品体验层：进度能不能看到、错误能不能就地改、成功有没有证据、能不能多走一步但不擅做。
- 几个具体方向：① 长任务的心跳式进度反馈；② 与产出颗粒度对齐的 inline 反馈通道；③ 带证据的成功/失败判定；④ "顺手做"建议而非自作主张；⑤ 接管后能断点续跑而不是从头开始。
- 一句话：**AI 产品的体验下半场，是"可感知的控制力"的竞赛**。

**避坑**：
- 不要预测具体时间线（"明年一定会怎样"），这类预测基本都会被打脸。
- 不要把某个细分体验点说成"唯一解"，保持开放。

---

## 六、落地建议类

### Q12：团队现在想试点，从哪类需求开始最容易拿到正反馈？

**短答**：选三类：**① 文档/知识类**（写 Spec、写复盘、写 release note、生成周报）；**② 增量小功能**（现有项目上的单页/小组件/E2E 补全）；**③ 兜底类工作**（CR 辅助、lint/一致性检查、重复代码批量改）。避开核心链路、数据变更、跨团队强依赖的需求。

**展开**：
- 文档类是最佳起点：风险低、产出可见、容易让人感受到"AI 省时间"，而且人对文档的容错度比对代码高。
- 增量小功能是第二阶段：前提是仓库有比较好的 README/AGENTS.md 类文档，AI 能自己读明白规矩。
- 兜底类工作（CR、测试补全、重复改造）性价比最高：它本来就是人不想干的事，AI 干了人最感谢。
- 团队启动的三个动作：① 先挑 1–2 个项目补全 README/AGENTS.md；② 选 2–3 个真实小需求跑一遍，别用玩具 demo；③ 跑完做复盘，把经验回写到 AGENTS.md 里，让下一次更顺。
- **别上来就搞"全员 AI 化"、"AI 写代码革命"这种大运动**，用试点小胜利建立信心最重要。

**避坑**：
- 不要给"试点必成功"的承诺——AI 今天还不是开箱即用，前几次一定有磨合成本。
- 不要让试点演变成"AI 写代码比赛"或"AI 取代谁"的焦虑话题，明确基调是"多一个协作伙伴"。

## 备用 Q&A（若时间允许）

### Q13：你这次用的什么模型？模型差异大吗？

**短答**：平台背后用的具体模型/多模型路由我不清楚（平台自己调度），但体感上**"系统设计 + 上下文质量"对结果的影响远大于模型本身的 benchmark 分数**。同样一个模型，在有 AGENTS.md 的仓库里和在一团乱麻的仓库里表现差很多。

**展开/避坑**：不要猜具体模型版本；不要说"某模型一定更强/更弱"；重点强调"工程化和产品设计的杠杆比换模型更大"。

---

### Q14：多 Agent 协作会不会出现"三个和尚没水喝"？比如 A 改的东西 B 又改回去？

**短答**：会有冲突风险，但因为所有 Agent 围绕同一个 Git 分支、同一套产物、同一份"项目宪法"工作，大部分冲突能靠规范和串行流转规避；真正的风险点是"Spec 变了但下游没感知"，所以 Spec 变更后要有机制让下游节点重跑。

**展开/避坑**：不要否认协同问题的存在；强调"共享上下文 + 串行流转 + 产物版本化"是解药；承认跨节点反馈循环（比如 CR 打回研发）是平台产品要持续打磨的地方。

---

### Q15：你自己之后还会用 AI 需求看板吗？什么场景下会用？

**短答**：会。但我会**选择性使用**：自己当 Owner、目标清晰、边界能说清、错了能回滚的事我会放心交给它；模糊度高、需要多方对齐、高风险的事我还是会自己操刀或让 AI 当助手而不是 Owner。

**展开/避坑**：不要说"以后所有需求都这么干"（不真实），也不要说"还是自己写靠谱"（浪费了已验证的效率红利）；坦诚是"看场景"最可信。
