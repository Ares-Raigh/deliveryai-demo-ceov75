# 为什么我要去跑这一次

- 团队在讨论 AI 协同研发，我不想空谈，想拿一次**真实的、从零到上线**的体感
- 之前对 AI 写代码的认知停留在"Copilot 补全几行"，想知道**当 AI 成为 Owner** 时会发生什么
- 想回答三个问题：
  1. 我**只写一段需求描述**，AI 能把事情做到几成？
  2. 中间**哪些地方我必须介入**，介入的成本有多大？
  3. 如果我们自己做 AI 产品，**哪些体验细节决定了它"像人"还是"像工具"**？

> 选的需求载体：在已有的"沸点火锅点单 Demo"上，加一个 PM 任务看板 + 周报生成 MVP（含前端页面、路由、数据、GitHub Pages 部署适配）。
> 这是一个**复杂度刚刚好**的需求：小到 AI 能 hold 住，大到能暴露问题。

# 全局视角：这条流水线长什么样

[截图位：DeliveryAI 需求看板的节点流程图（需求设计 → 代码开发 → 自动化测试 → 代码 Review → 发布部署验证），P5]

```
┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐   ┌────────────┐
│ 需求澄清    │ → │ 代码开发    │ → │ 自动化测试  │ → │ 代码 Review │ → │ 发布部署验证│
│ (Spec 生成) │   │ (编码 Agent)│   │ (测试 Agent)│   │ (CR Agent) │   │ (发布 Agent)│
└────────────┘   └────────────┘   └────────────┘   └────────────┘   └────────────┘
        ↑                                                                ↓
        └──────────── 失败/阻塞时可回滚、重试、人介入 ←─────────────────────┘
```

- 整个流水线**默认自动往下走**，每个节点结束会自动触发下一个
- 节点之间通过两类东西传信息：
  - **artifacts（产物）**：结构化文档、测试报告、CR 意见，挂在任务上随版本累积
  - **Git**：代码、分支、commit 是"硬通货"
- 人可以在任何节点**插进来**：评论、改 Spec、回滚、手动触发、接管
- 下面我按节点顺序，一个一个讲我的体感

# 节点 ①：需求输入 + 需求澄清（我在做什么）

**我做了什么**
- 贴了一段自然语言需求 + 选了仓库
- 点了"开始"
- 然后……**没我事了**，等 AI 出 Spec

**AI 做了什么**（推断：需求澄清 Agent 基于工作流命名与产物结构）
- 读仓库的 README、AGENTS.md、现有代码结构
- 把我那段话扩成一份结构化的 Spec（目标、范围、验收标准、约束、待确认问题）
- 主动列出几个它不确定的点，准备让我确认

**产物**
- `artifacts/需求设计/需求说明/Spec.md`（几千字的结构化文档）
- 一份**待确认问题清单**（本次 Spec 里列了 5 个，包含素材缺口、时长、交付形态等）

[截图位：需求澄清节点的 Spec 输出页，展示目录结构与待确认清单，P6]

> 这是第一个让我"哇"一下的节点。我写了大概 300 字，它吐回给我一份**比我自己写得还规整**的 PRD 雏形。

---

# 节点 ① 的真实感受：它比我更懂"怎么开工"

惊艳的地方：
- **它先读规则再动手**——仓库里的 AGENTS.md、目录约定、编码规范、测试规范、发布 runbook 都被它啃了一遍，后续所有动作都遵守了
- **它会主动说"我不确定"**——待确认清单是真问题，不是凑数（"你要 30 分钟还是 45 分钟版？""要不要部署在线版？"）
- **它把 Out of Scope 写得很清楚**——这一点比很多 PM 写的需求都强

但也有机器味：
- 它列出的问题是**结构正确但惊喜不足**的——没有问出那种"你其实想的是 X 对不对？"的洞察性问题
- Spec 的措辞有点"咨询报告腔"，需要我自己过一遍把语气拉回到真诚

> 💡 体验感受：**像一个训练有素但刚入职的 BA**，基本功到位、不越界、不装懂，但还不会替你多想一步。

---

# 节点 ②：代码开发（它是怎么写代码的）

**我做了什么**
- 看完 Spec，确认默认推荐项（40 分钟标准版 / Slidev 格式 / 双轨交付），点了继续
- **中间基本没动手**——让它自己写

**AI 做了什么**（推断：研发编码 Agent）
- 在工作分支 `docs/ai-board-sharing-docs-k0dr` 上开工
- 先读了现有的 `src/` 结构、`tailwind.config.js` 色板、`components/ui/` 通用件
- 新增 PM 任务看板视图、`useViewRoute` 注册、reducer 加任务流转逻辑、i18n 中英文、周报生成按钮
- 自己发现 GitHub Pages 子路径部署问题，补了一个 `vite base='./'` 的 fix

**产物**
- 两次关键提交：
  - `418fc3e feat(pm-task-board): 任务看板与周报生成 MVP`
  - `3f65971 fix(pm-task-board): set vite base=./ for GitHub Pages project-site deployment`
- 代码遵守了仓库既有约定（色板、命名、无后端调用、Dialog/Button 用 ui 组件）

[截图位：GitHub commits 页面，展示两次提交；或任务看板代码 diff 片段，P8]

---

# 节点 ② 的真实感受：执行力 > 创造力

惊艳的地方：
- **对既有代码的"读-跟-写"能力很强**——新代码的色板、命名、目录位置都和老代码"长得像一家人"，这一点比很多跨组协作的 junior 工程师做得好
- **会主动做工程化收尾**——自己加 commit message、自己处理 base 路径问题，不是"写完就算"
- **不越界**——AGENTS.md 写了"不引入后端 API 调用、不引入额外 UI 库"，它真的没引

卡点的地方：
- 如果我不主动给它"必须遵守 AGENTS.md"的约束，它早期方案里其实出现过想引新依赖的倾向（推断：基于常见 LLM 行为模式）
- **遇到架构级选择会保守**——它会选"最安全、最像已有代码"的方案，不会替你重构或做更大胆的设计决策
- commit 粒度偏粗，一次提交包了多个改动点，CR 时不够友好

> 💡 体验感受：**像一个执行力很强、听话、但需要你把边界画清楚的中级工程师**。你给它一个"在现有框架里做增量"的任务，它能 80 分完成；你要它做架构决策，得你拍板。

# 节点 ③：自动化测试（AI 测 AI）

**我做了什么**
- 没动手，节点自动触发

**AI 做了什么**（推断：测试 Agent）
- 读了 `docs/agent-testing.md` 里的 E2E 规范（不用 `waitForTimeout`、`getByRole` 优先、webServer 自动拉起等）
- 基于需求验收点写 E2E 用例：视图路由、看板列切换、任务流转、周报弹窗
- 跑完一遍收集失败，一次性批量修复，再全量跑绿
- 产出 playwright-report（HTML 报告）

**产物**
- `e2e/` 下新增/更新的 spec 文件
- 终端输出的 PASS/FAIL 记录
- HTML 测试报告（带截图/trace）

[截图位：Playwright 终端输出全绿截图，或 HTML 报告摘要，P10]

---

# 节点 ③ 的真实感受：它比人守规矩

惊艳的地方：
- **它真的会读测试规范**——`docs/agent-testing.md` 里写的"首轮收集所有失败后批量修复""`getByRole` 优先""不装浏览器"这些细节，它真的照做了
- **写断言比人严谨**——正反路径都覆盖了（比如"超级辣弹提示、其他辣度不弹"这种正反模式，它写得比我自己写得全）
- 不会疲劳、不会觉得"这个 case 太简单算了"

卡点/槽点：
- **用例命名和注释有点机械**——`REQ-001 should work` 这种命名虽然合规，但人读起来需要点适应成本
- **它不会质疑需求本身**——如果 Spec 里漏了一个边界，它就不测那个边界，不会像老测试一样问一句"这个情况要不要考虑？"
- 测试失败时它倾向于"修到过"而不是"停下来想是不是需求理解错了"，某些情况下会修出迎合错误期望的用例（推断：基于 LLM 一般行为，本次体验中未出现严重此类问题）

> 💡 体验感受：**像一个刚毕业但非常守规矩、非常耐心的测试同学**，执行力满分，质疑精神零分。需要人来决定"测什么"，它负责"测到位"。

# 节点 ④：代码 Review（CR Agent 上来挑刺）

**我做了什么**
- 没动手，节点自动触发

**AI 做了什么**（推断：CR Agent）
- 对着本次 diff 跑一轮 Review：命名、边界处理、i18n 中英文对齐、是否违反 AGENTS.md 约定、是否有潜在空值/状态错乱
- 产出一份结构化的 CR 意见（问题级别：必改 / 建议 / nit）
- 如果有必改问题，会打回研发节点让它修；没有则通过

**产物**（本次实际产物请在分享前补真实截图）
- CR 意见文档（挂在 artifacts 上）
- 必要时自动触发的修复提交

# 节点 ④ 的真实感受：它挑的错和人不一样

惊艳的地方：
- **对"一致性"类问题特别敏感**——"这里用了 `bg-chili-500`，那处类似语义用了 `bg-red-500`"、"zh 文案有这句，en 没同步"，这种问题人 CR 很容易漏，它几乎不漏
- **对约定条款的遵守是硬约束**——AGENTS.md 里写过"不要做"的事情如果被碰了，它一定会抓出来
- **不会因为关系好就放水**😂

槽点：
- **对"业务逻辑合理性"的判断弱**——它能看出"你写的和你说的不一致"，但看不出"你写的虽然和你说的一致，但业务上这么做不对"
- **偶尔会 nit 过度**——一些纯粹风格偏好的问题也会提，信噪比不如资深工程师高
- **它没看过产品**——没有视觉和产品视角，只能对代码做静态审查

> 💡 体验感受：**像一个严格但没有产品 sense 的 linter 升级版**。代码质量兜底很靠谱，但替代不了"有业务判断的人"做最终把关。

# 进入最值钱的部分：7 条体验洞察

接下来我按"**场景 → AI 实际表现 → 我的感受 → 对做产品的启发**"四段式讲 7 条洞察，不按节点按**体验主题**组织。

# 洞察 1：它先读规则再动手

::left::

**场景**：需求澄清完进入研发，我没给任何编码提示，它自己先把仓库里的 AGENTS.md、tailwind 色板、i18n 模式、测试规范、发布 runbook 全扫了一遍。

**AI 表现**：后续所有产出——新组件用的颜色类名、i18n key 命名、Dialog 用法、E2E 定位器策略、部署核验步骤——**全部踩在仓库约定上**，几乎没有需要我纠正"我们不这么写"的地方。

**感受**：**惊艳**。这是第一次我在 AI 协作里没有因为"它不了解上下文"而血压升高。

::right::

**💡 给我们做产品的启发**：

> **上下文加载不是锦上添花，是地基。**

- AI 产品必须给 Agent 提供"上岗培训包"：AGENTS.md 这种"项目宪法"级文档是第一公民
- **不要让用户每次都重复说一遍规则**——规则应该被沉淀、被版本化、被自动加载
- 反过来讲，**只要你的产品里 Agent 每次都要用户重新教"我们怎么做"，体验就直接垮掉**

# 洞察 2：主动说"我不确定"

::left::

**场景**：需求澄清阶段，Spec 末尾列了 5 个待确认问题（时长、是否部署在线版、交付形态等），没有自作主张选一个直接往下做。

**AI 表现**：把问题、选项、影响、推荐默认值都写清楚了，让我拍板。对于真的没有信息可以推断的点，它选择**停下来问**。

**感受**：**像人一样顺畅**。不怕 AI 问问题，就怕 AI 不问问题直接做错了之后我来擦屁股。

::right::

**💡 给我们做产品的启发**：

> **HITL（Human-in-the-loop）的开关，应该由"不确定性"驱动，不是由"节点"驱动。**

- 不要死板地"每个节点都必须人确认"，那是工作流不是 AI 协同
- 也不要"全自动不打断"，那一定会在关键处翻车
- 判断标准：**AI 自己的置信度 + 决策的不可逆程度 + 纠错成本**。高不确定 + 高纠错成本 = 必须打断问人；低不确定 + 低纠错成本 = 闷头做
- 问问题的时候要给**推荐默认值**，不要把空白抛给用户

# 洞察 3：产物沉淀带来"反查快感"

::left::

**场景**：跑完整个流程回头看，每个节点都有可读产物：Spec.md、commit、E2E 报告、CR 意见、发布记录，全部挂在任务上，版本可追溯。

**AI 表现**：不是"做了就做了"，而是**每一步都留下人能读的东西**，甚至 artifacts 有 `_manifest.json` 做版本索引。

**感受**：**顺滑 + 可控感**。我知道我随时能回去看它当时在想什么、做了什么，不是黑箱。

::right::

**💡 给我们做产品的启发**：

> **AI 产品必须让用户"反查得到"。**

- 没有可追溯产物的 AI 协作 = 黑箱魔法，用户不敢用在正事上
- 产物要**人可读**，不是只给机器看的 JSON；Markdown 是最佳公约数
- 版本化和 manifest 这种"看起来很工程化"的东西，对信任感的贡献非常大
- 一句话：**让用户感觉"我随时能接管"，他才敢放心放权**

# 洞察 4：卡点一——进度不透明

::left::

**场景**：代码开发节点，AI 开始写代码后界面长时间处于"执行中"状态，我看不到它在做什么、做到哪了、会不会卡住。

**AI 表现**：（推断）平台会流式输出思考/日志，但在我那次体验里中间有一段"沉默期"，看不到 sub-agent 的具体动作，只能等结果刷新。

**感受**：**卡顿 + 焦虑**。不知道它是在认真写代码，还是已经挂住了。这种焦虑感和命令行跑一个没日志的长任务是一样的。

::right::

**💡 给我们做产品的启发**：

> **AI 干活时必须"出声"，哪怕只是说"我正在读 XX 文件"。**

- 进度反馈的本质不是"准确的百分比"，而是**"还活着、在推进、方向对"** 三个信号
- 至少要暴露：当前在哪个子步骤、已经做了什么、下一步做什么
- 长任务要有"心跳"——哪怕只是每隔 N 秒打一行当前动作
- 用户最怕的不是慢，是**不知道它是不是死了**

# 洞察 5：卡点二——纠错路径不顺

::left::

**场景**：测试节点里，如果 AI 写错了一个用例或误解了一个验收点，我怎么让它改？

**AI 表现**：（推断）当前主要通过节点上评论/回滚/重试来纠偏，但**"在 diff 的具体某一行上说这句话不对"**这种颗粒度的反馈通道不够顺；评论也没有结构化地"告诉 AI 该怎么改"，有时需要重跑整个节点。

**感受**：**机器味明显 + 挫败**。人协作时我可以指着代码说"第 42 行这个判断应该反过来"，AI 协作时我要想好"怎么描述才能让它精准听懂"。

::right::

**💡 给我们做产品的启发**：

> **反馈颗粒度要和产出颗粒度对齐。**

- AI 产出了代码 diff，我就应该能**在 diff 上直接打评论**让它改
- AI 产出了文案，我就应该能**选中一句话**让它重写
- 不要让用户退回到"重新写一整段 prompt"的颗粒度去修正细节
- 每个"接管入口"旁边都要有一个"让 AI 按我的批注再改一次"的按钮，而不是只有"重跑节点"

# 洞察 6：卡点三——成功/失败的信号太弱

::left::

**场景**：发布节点结束，它说"部署成功"，但页面上的成功提示和它处理中、甚至它失败时的提示，视觉上没有本质差别；我要自己去点链接、自己 curl、自己去 Actions 看一眼才放心。

**AI 表现**：最终的核验结果是结构化的（200/关键文案存在），但这个"置信信号"没有强到让我**不自己验一遍**。

**感受**：**无感 + 不信任**。我知道它大概率对了，但我还是要点一下。这种"AI 做完了我还得亲自验"的感觉，就是体验的隐形税。

::right::

**💡 给我们做产品的启发**：

> **信任不是说出来的，是"证据"摆出来的。**

- "成功"页不要只有一个绿勾，要给出**可核验的证据**：部署 URL、关键响应、截图、日志片段
- 失败不要只说"失败了"，要直接告诉用户**哪一步挂了、AI 已经尝试过什么、建议你下一步做什么**
- 把"AI 做了哪些自检验证"显式列出来，比一句"部署成功"可信 10 倍
- 最好的状态：**用户看一眼证据就敢信，不必自己再验**

# 洞察 7：卡点四——它不会"替我多想一步"

::left::

**场景**：研发完成后，它帮我把 base 改成 `./` 适配 GitHub Pages——这是它主动做的，很加分。但除此之外，它不会主动说"你要不要顺手把 README 更新一下？""这个新增页面要不要加到导航里？""你提到要分享，要不要顺手生成一个 Slidev 版本？"

**AI 表现**：**严格按 Spec 交付**，一件不多一件不少。超出 Spec 的事情除非我明确说，否则不做。

**感受**：**机器味明显**。和一个靠谱同事的差别就在这里——同事会说"顺手帮你把 XX 也弄了"，AI 不会。

::right::

**💡 给我们做产品的启发**：

> **AI 产品应该有"多走一步"的选项，但不要自作主张。**

- 完成主任务后，给出 **3 个以内** 的"顺手可以做"建议（更新 README/补截图/加埋点），让用户一键选
- 默认**不做**，避免越帮越忙；但要**主动提**，体现主动性
- "多走一步"的判断标准：**可逆 + 低成本 + 高概率被需要**
- 这一步做好了，AI 才会从"好用的工具"变成"贴心的同事"

# 启示一：做 AI 产品，先设计"Agent 上岗培训"

- **AGENTS.md 模式值得所有 AI 产品抄**。每个项目/任务/空间都应该有一份"宪法"：
  - 项目是什么、技术栈/规则是什么、哪些不能做
  - 验证命令、目录约定、风格约定
  - Agent 做错了会有什么后果
- 这份"宪法"要**被自动读取、被版本化、被强制执行**，而不是放在某个角落里让用户每次复制粘贴
- 更进一步：**让 AI 自己维护这份文档**——当它发现新约定时，主动提议更新

---

# 启示二：HITL 是产品设计问题，不是技术问题

- 很多 AI 产品在 HITL 上的做法很懒：要么全自动不打断（翻车率高），要么每步都要点确认（体验像审批流）
- 真正好的 HITL：
  1. **判断何时打断**：基于置信度 × 不可逆程度 × 纠错成本
  2. **打断时给足上下文**：告诉用户我为什么问、我已经知道什么、我推荐什么
  3. **给用户"接管粒度"的选择**：是改一个词、改一段话、还是全部自己来
  4. **接管完了之后 AI 要能接回去继续跑**，不要从头开始
- 这四步做好，AI 才从"自动脚本"升级为"协作者"

---

# 启示三：可解释性 > 智能感

- 这次体验里，**让我信任的瞬间不是"它好聪明"，而是"它做的每件事我都查得到"**
- 做 AI 产品容易陷入一个误区：追求"哇塞 AI 好强"的瞬间。但真正让用户**敢用在工作里**的是：
  - 做了什么、为什么这么做，**事后能看**
  - 做错了**能定位到哪一步错的**
  - 想接管**能无缝接过来**
- **可解释、可追溯、可接管**——这三个"可"比 benchmark 分数高 10 个点重要得多

---

# 如果团队想试点，我建议这样起步

1. **选对第一批需求**：边界清晰、上下文充分、错了能回滚的增量需求（文档生成、单页模块、CR 辅助、测试补全）。不要一上来就让 AI 动核心链路。
2. **先写"宪法"再让 AI 上场**：每个项目备一份 AGENTS.md 式的约束文档，越具体 AI 表现越好。
3. **保留强制人工卡点**：上线前的业务验收、对外口径、数据变更、安全相关，必须有人签字。
4. **把"AI 产物"当成一等公民**：Spec、测试报告、CR 意见都要可读、可版本化、可 diff，不要只留最终代码。
5. **复盘，而不是神话**：每次 AI 做需求，都留一个"哪里好哪里不好"的小复盘，喂回给规则/提示词/流程——AI 系统本身也需要迭代。
